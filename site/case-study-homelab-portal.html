Homelab Portal

A two-tier Flask + PostgreSQL application that monitors real homelab infrastructure live, deployed on AWS EC2 with a self-hosted Jenkins pipeline that reaches back into the on-prem homelab over Tailscale — built to demonstrate full-stack development, CI/CD, containerization and hybrid cloud architecture together.

View on GitHub Get in touch

Architecture

The app's entire purpose is monitoring homelab infrastructure, which creates a real architectural question once it's hosted in the cloud: how does a cloud-hosted app reach securely back into private on-prem infrastructure? The homelab already runs Tailscale for remote access — joining the EC2 instance to the same tailnet extends that trust boundary instead of building a separate, weaker one with public ports.

Two VMs, one shared purpose on the on-prem side: Jenkins runs alone on its own VM, kept separate from where the monitored infrastructure actually lives, so a compromised build never has a direct path to anything else.

CI trigger git push → Jenkins Poll SCM (no port forwarding into the homelab)
Deploy Jenkins checks EC2 state → starts it if stopped → polls real SSH readiness → redeploys
Live data EC2 → Tailscale → Proxmox API (VM status) + forced-command SSH (Docker/disk)
Access Browser → Tailscale → EC2:5000, session login required

Security model

Every credential in this project is scoped to the minimum it needs:

  • Proxmox API token — the built-in PVEAuditor role: read-only, can see status but can't start, stop or modify anything.
  • SSH "agent" key (live Docker/disk data) — restricted via an OpenSSH forced command= to running exactly two whitelisted operations, nothing else, no shell.
  • SSH "deploy" key (Jenkins → EC2) — same forced-command pattern, allow-listed to a health check and the redeploy script only.
  • IAM user for EC2 auto-start — ec2:StartInstances scoped to this exact instance ARN; ec2:DescribeInstances forced to a wildcard resource by AWS's own API, not a looser choice.
  • No Elastic IP, no public inbound ports beyond Tailscale's own UDP port — not even SSH is reachable from the open internet; every connection goes over the tailnet.
  • The app itself is login-gated (session-based, password stored as a salted hash), not just left open to anyone who finds the address.

CI/CD pipeline

Every push to main runs a real four-stage pipeline: Build (tagged with both a build number and latest), Test (a throwaway Postgres and the newly built image on an isolated Docker network, polled against the image's own health check until it reports healthy or the stage fails with logs attached), Push (only reached if Test passed), and Deploy.

Deploy is the interesting stage: since EC2 isn't running 24/7, it first checks AWS's reported instance state, starts the instance if it's stopped, waits for AWS's own "running" confirmation — and then separately polls for actual SSH reachability, because AWS reporting "running" and the OS/SSH daemon being genuinely ready are two different moments. Trusting the first one alone made the pipeline flaky in practice.

Database migration

Real inventory data was migrated from the original on-prem deployment to EC2 using pg_dump/psql — the standard approach for any Postgres migration regardless of scale. A --data-only dump avoided schema collisions (the schema already existed identically on both sides, since both run the same app code), and TRUNCATE ... RESTART IDENTITY CASCADE cleared test data on the target while resetting ID sequences before the restore, so migrated rows kept their original IDs without conflicts.

Bugs found and fixed

  • Gunicorn multi-worker race condition. Table creation ran at module import time, meaning every worker process executed it independently on startup. Against a genuinely empty database (exactly what the Test stage always uses), two workers raced to create the same table and one crashed on a duplicate-key error. Fixed with preload_app so initialization runs once before forking, plus a post_fork hook giving each worker its own fresh database connection.
  • Docker Compose interpreting $ as a variable reference. Scrypt password hashes contain $ delimiters; Compose silently swallowed part of a hash as an undefined variable until it was escaped as $$.
  • A forced-command SSH health probe rejected by its own security restriction. The Jenkins readiness check called an arbitrary command over SSH; the deploy key's forced-command wrapper correctly rejected it as unrecognized, since it was only ever allow-listed to run one specific redeploy script. The fix added a second, minimal allow-listed command for health checks — the restriction was working exactly as designed throughout; the probe just needed to respect it.

Cost

Designed to stay low cost at real usage: the EC2 instance runs only when needed, not 24/7, with Jenkins automatically starting it on deploy. No Elastic IP (unnecessary cost, and unneeded since Tailscale provides stable addressing regardless of the instance's AWS-assigned IP across stop/start cycles). The EBS volume is the one cost that exists regardless of usage, and it's small.

What's next
