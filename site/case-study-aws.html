Secure Static Portfolio on AWS

A personal portfolio site running on a fully automated, monitored, and Infrastructure-as-Code-managed AWS architecture — built to demonstrate real cloud architecture, security and operational decisions, not application code.

View on GitHub Get in touch

Architecture

Content delivery, deployment, cache automation and monitoring are four separate, deliberately decoupled flows — each does one job, so a failure or change in one doesn't ripple into the others.

Every box in this diagram is defined in Terraform and was adopted via terraform import against already-running infrastructure — nothing here was recreated to get it under IaC.

Content delivery Internet → CloudFront (OAC, HTTPS) → S3 (private)
Deployment git push (site/**) → GitHub Actions (OIDC) → S3
Cache automation S3 object change → Lambda → CloudFront invalidation
Observability Lambda errors / CloudFront 5xx → CloudWatch Alarm → SNS → Email

Security model

This project deliberately avoids the common "S3 static website hosting + public bucket" tutorial pattern. Instead:

  • Block Public Access is enabled on the bucket — no ACLs, no public bucket policy, no exceptions.
  • Origin Access Control (OAC) is the only path into the bucket, via a SigV4-signed request. Verified directly — a raw request to the S3 object URL was tested and confirmed denied.
  • No long-lived AWS credentials anywhere in CI. GitHub Actions authenticates via OIDC: a short-lived, signed token presented directly to AWS STS, never a stored access key.
  • Three IAM identities, each scoped to exactly what it needs:
    • The human operator user — resource-scoped to this project's exact S3 bucket, CloudFront distribution, Lambda function and IAM roles, not broad service wildcards.
    • The Lambda execution role — one action (cloudfront:CreateInvalidation), one resource.
    • The GitHub Actions role — S3 sync permissions only. No CloudFront access at all; invalidation is the Lambda's job, kept deliberately separate.
  • Root is never used day-to-day, and has MFA enabled.

Automation & monitoring

An S3 "object created" event triggers the Lambda, which calls CloudFront's create_invalidation API — no manual cache-clearing step exists anywhere in this project. Deploys are triggered by a push to main under site/, authenticated via OIDC.

Two CloudWatch alarms watch the parts of the system most likely to fail silently: Lambda errors, and CloudFront's 5xx rate. Both notify a region-appropriate SNS topic by email, and both were tested end-to-end by deliberately breaking a permission, confirming the alarm fired and the email arrived, then restoring it — not just configured and assumed working.

Infrastructure as Code

Everything above is defined in Terraform and was brought under management via terraform import against the already-running, already-live infrastructure — deliberately not recreated from scratch, to avoid any risk of downtime or a changed CloudFront URL during the migration. Every import was followed by terraform plan to confirm zero drift before moving to the next resource.

Deliberately left unmanaged (referenced by ARN/value only): the WAF Web ACL discovered during this migration (see Lessons learned), the customer-managed IAM policy the Lambda console auto-generates for logging, and the operator IAM user itself — it's the identity running Terraform, so it's kept out of self-management on purpose.

Cost

Designed to stay effectively free at portfolio-site traffic levels: S3, CloudFront and Lambda all sit comfortably inside free-tier allowances (Lambda's is permanent, not time-limited). No custom domain, no RDS, no always-on compute. An AWS Budget alarm was configured before any resource was created, as a safety net.

Lessons learned

  • The CloudFront origin path is a path inside the bucket, not the bucket name — an early misconfiguration caused 403s until corrected.
  • GitHub's OIDC sub claim uses an immutable numeric ID format, not the human-readable repo:owner/repo:ref:... form most examples show. Diagnosed via CloudTrail by checking the actual claim AWS received on a failed AssumeRoleWithWebIdentity call.
  • An unintended AWS WAF Web ACL was found attached to the distribution mid-migration — never deliberately configured, almost certainly opted into via a console default. WAF has no free tier; Cost Explorer confirmed $0 actually billed, and it was evaluated deliberately rather than reflexively removed.
  • The Lambda console's "basic execution role" default doesn't attach the AWS-owned managed policy — it clones it into a customer-managed policy first. Only discovered because Terraform's import failed against the ARN that seemed correct.
  • New AWS Lambda runtimes can outpace Terraform provider support — a real, if temporary, tooling gap rather than a configuration mistake.
  • Least-privilege IAM is iterative, not one-shot. Nearly every phase of this project surfaced a permission gap only discoverable by actually hitting it.
